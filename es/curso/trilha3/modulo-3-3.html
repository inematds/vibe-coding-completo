MÓDULO 3.3

📚 Biblioteca de prompts listos (copy-run)

Ocho prompts reales, completos y listos para pegar, cubriendo todo el proceso: desde la configuración del proyecto hasta la auditoría de seguridad de una app. Cada tema es una receta: objetivo, el prompt en sí (con partes variables entre <assim>) y cómo verificarlo. Reemplaza las variables con tu caso y ejecútalo.

📋 Cómo usar la biblioteca

Cada prompt es independiente: usa lo que necesites, en el orden que tenga sentido. Las partes entre <assim> son variables: adáptalas a tu caso. Regla de oro: las claves y los secretos siempre van en el archivo de entorno (.env), nunca pegados en el chat. Comienza las construcciones en Plan Mode (consulta el módulo 3.2).

Los ocho prompts cubren el ciclo de vida de un proyecto: preparas el terreno (1-2), construyes y corriges (3-4), mejoras (5), empaquetas la reutilización (6) y llevas todo a producción (7-8). Es la biblioteca que vuelves a consultar con cada nuevo build.

1

📄 Setup & CLAUDE.md

Qué es

El primer prompt de todo proyecto: generar el CLAUDE.md, el system prompt persistente que define quién es la IA, qué estás construyendo y cómo debe ayudarte. Está escrito en markdown y se guarda en la raíz de la carpeta del proyecto.

¿Qué es?CLAUDE.md — un archivo de texto que la IA lee en cada sesión; funciona como una «ficha de incorporación» con el rol, el contexto, las reglas y el estilo. Mantenlo conciso (pocos cientos de líneas).

Por qué aprender

Sin CLAUDE.md, vuelves a explicar el contexto en cada conversación. Con él, la IA ya conoce el objetivo del proyecto y tus preferencias desde el primer mensaje, y puedes iterar el archivo simplemente conversando.

🎯 Objetivo: crear el CLAUDE.md inicial del proyecto.

prompt (cópialo y ejecútalo en Plan Mode, en la carpeta vacía del proyecto)
Crie um arquivo CLAUDE.md na raiz deste projeto. Ele é o system prompt
persistente que você vai ler em toda sessão. Inclua estas seções:

- Papel: você é <ex.: um assistente de automações n8n>.
- Contexto: estou construindo <ex.: workflows de IA para uma agência>.
- Como ajudar: me ajude a planejar, construir, depurar e otimizar.
- Preferências: explicações concisas e diretas; português; descreva o resultado
  e me pergunte quando faltar informação.
- Regras: procure uma ferramenta existente antes de criar uma nova; quando algo
  falhar, diagnostique e aprenda; mantenha este arquivo atualizado; nunca peça
  para eu colar chaves no chat (use o .env).

Mantenha enxuto (poucas centenas de linhas). Depois, me mostre o arquivo.

✅ Cómo verificar: el archivo CLAUDE.md existe en la raíz, con las secciones solicitadas y una extensión razonable. Ábrelo y léelo para confirmar que el rol y el contexto son correctos; si quieres, pide ajustes conversando.

Conceptos clave

Carpeta dedicada

Un proyecto por carpeta.

System prompt

Leído en cada sesión.

Conciso

Solo lo esencial.

Iterable

Edita conversando.

2

🔌 Conectar una herramienta mediante MCP

Qué es

El prompt para darle «brazos» a la IA: instalar un MCP server que expone un conjunto de herramientas externas (raspar la web, leer bases de datos, comunicarse con apps). La configuración está en .mcp.json a nivel del proyecto, y la clave de API va en el .env — tú lo pegas manualmente, nunca en el chat.

¿Qué es?MCP (Model Context Protocol) — un protocolo en el que una conexión expone varias herramientas; la IA decide cuál usar y cuándo. .mcp.json — el archivo de configuración del server. /mcp — el comando que enumera los servers conectados.

Por qué aprender

Sin MCP, la IA solo lee y escribe archivos. Con MCP, actúa en el mundo. Configurarlo a nivel del proyecto (no global) evita avisos de seguridad en cada reinicio, y leer la clave de .env mantiene el secreto fuera del código.

🎯 Objetivo: instalar y conectar un MCP server con la clave en .env.

prompt (cópialo y ejecútalo)
Instale o MCP server de <ex.: Firecrawl, para busca/scraping na web> neste
projeto, com a configuração no NÍVEL DO PROJETO (não global).

Passos:
1. Use o comando de instalação para Claude Code da documentação oficial:
   <cole aqui o comando de instalação do provedor>
2. Gere/atualize o .mcp.json com a entrada do server e um placeholder de API key.
3. Garanta que a chave seja lida do arquivo .env — NÃO me peça para colar a
   chave aqui no chat. Apenas me diga o nome da variável a preencher no .env.
4. Ao final, faça uma verificação de conexão (status do server).

Se o server não aparecer, me lembre de reiniciar o Claude Code.

✅ Cómo verificar: ejecuta /mcp y confirma que el server aparezca en la lista con estado saludable. La clave está en el .env (que está en el .gitignore), no en el chat ni en el .mcp.json.

🎯 Consejo práctico

Si el server no aparece después de instalarlo, reinicia Claude Code antes de cualquier otra cosa: eso lo resuelve la mayoría de las veces.

Conceptos clave

.mcp.json

Configuración del server.

Project-level

No global.

Clave en .env

Nunca en el chat.

/mcp

Verificar conexión.

3

🧱 Crear un workflow desde cero

Qué es

O prompt de apertura integral: una única solicitud que describe el resultado, la fuente de datos y el destino, y deja que la IA decida la arquitectura (incluso cómo almacenar/buscar documentos). Es "un prompt para gobernarlos a todos" — empezar bien aquí ahorra muchas idas y vueltas.

Por qué aprender

En lugar de dictar "use un vector store", describes el problema y dejas que la IA proponga el mejor enfoque (system prompt para documentos pequeños; vector store para escalar). Pregunta lo que falte y tú apruebas el plan antes de construir.

🎯 Objetivo: iniciar una build completa con un solo prompt (ejemplo: agente de soporte por correo electrónico).

prompt de apertura (Plan Mode)
Entre em plan mode. Quero o resultado a seguir, e você decide a arquitetura.

Objetivo: um agente que lê os e-mails recebidos, identifica perguntas de suporte
técnico e rascunha uma resposta baseada nas nossas políticas. Anexei os documentos
<ex.: politicas.pdf e faq.pdf> na pasta do projeto.

Requisitos:
- Use as informações dos documentos como fonte da verdade; não invente.
- E-mails que não forem de suporte devem ser ignorados.
- Quando não houver resposta nos documentos, NÃO invente: avise que vamos
  pesquisar e retornar.

Antes de construir: leia os documentos, decida como armazená-los e buscá-los
(system prompt vs. vector store, escolha e justifique), me faça as perguntas de
esclarecimento e proponha o plano com a lista de credenciais. Não construa até
eu aprovar.

✅ Cómo verificar: la IA leyó la documentación, propuso una arquitectura justificada (p. ej., un vector store por escalabilidad), preguntó lo que faltaba y enumeró las credenciales. Aprueba solo cuando el plan tenga sentido.

Conceptos clave

Integral

Resultado + fuente + destino.

La IA decide

La arquitectura.

No inventes

Fuente de la verdad.

Aprobar

Antes del build.

4

🐞 Depurar un error

Qué es

O plantilla de troubleshooting listo: pega el mensaje de error literal, di dónde ocurrió y qué esperabas, y pide la causa + una corrección puntual. Sirve tanto para errores locales como para fallas que solo aparecen en producción (en trazas de ejecución).

Por qué aprender

La IA corrige rápido cuando recibe contexto, y lento (o se equivoca) cuando solo recibe "hubo un error". Esta plantilla estandariza lo que necesita: el error exacto, el lugar y lo que se esperaba.

🎯 Objetivo: una plantilla reutilizable que hace que la IA diagnostique y corrija.

plantilla de debug (copia y ejecuta)
Deu erro. Contexto completo:

- Onde: <nó/passo/arquivo, ex.: "trace do passo 3, chamada à API X">
- O que eu esperava: <ex.: "que retornasse a lista de resultados">
- O que aconteceu: <sintoma observado>
- Mensagem de erro (literal):
"""
<cole o erro / trecho do trace EXATAMENTE como apareceu>
"""

Diagnostique a causa raiz, explique POR QUE aconteceu, e aplique a correção
mínima necessária. Não mude mais nada além disso. Depois, me diga exatamente
como reproduzir o teste para confirmar que foi resolvido.

✅ Cómo verificar: la IA señala la causa (p. ej., un formato de respuesta de la API distinto del esperado), aplica una corrección específica y te indica el paso de prueba. Vuelve a ejecutar; si aparece un error nuevo, repite la plantilla con el nuevo mensaje.

Conceptos clave

Error literal

Pega exactamente.

Local + esperado

Da el contexto.

Causa raíz

Pide el porqué.

Corrección mínima

Sin tocar el resto.

5

🎚️ Los 6 enhancements

Qué es

Seis prompts de mejora que transforman un agente de «funciona» en «funciona bien». Tres son de error/lógica (alternativa sin coincidencias, filtro por tiempo, filtro de automáticos) y tres de calidad del resultado (tono de marca, nombre del cliente, indicador de confianza). Aplica uno a la vez, basando la solicitud en el workflow existente, y prueba cada uno.

Por qué aprender

Estos seis cubren los casos límite más comunes de un agente real. Siempre asigna un nombre al workflow en la solicitud; sin eso, la IA puede crear un workflow nuevo en lugar de editar el tuyo. Y para probar un filtro, tienes que enviar exactamente el tipo de entrada que debe captar.

🎯 Objetivo: mejoras 1-3 (error/lógica), una por vez.

prompts (pega uno a la vez)
No workflow existente "<nome exato>", aplique UMA melhoria por vez:

[1] Fallback sem match: quando a busca na base não encontrar resposta, em vez de
    inventar, gere um rascunho educado dizendo que vamos pesquisar e retornar.
    Use um marcador de "encontrou/não encontrou" para decidir o caminho.

[2] Filtro por tempo: processe apenas entradas mais recentes que <ex.: 10 minutos>.

[3] Filtro de automáticos: ignore mensagens automáticas (no-reply, postmaster,
    ausência/out-of-office, newsletters, notificações de entrega). Marque com um
    sinalizador e desvie para "ignorar".

Edite ESTE workflow (não crie outro). Me explique o que muda antes de aplicar.

✅ Cómo verificar: para [1], envía una pregunta fuera de la base y comprueba que aparezca el borrador «vamos a investigar» (no una respuesta inventada). Para [2]/[3], envía exactamente el tipo de entrada que debe detectar el filtro y confirma que se desvíe.

🎯 Objetivo: mejoras 4-6 (calidad de la salida), una por vez.

prompts (pega uno a la vez)
No workflow existente "<nome exato>", aplique UMA melhoria por vez:

[4] Tom de marca: ajuste o tom das respostas para <ex.: amigável, prestativo,
    informal, entusiasmado>. Atualize tanto a resposta principal quanto o
    rascunho de fallback.

[5] Nome do cliente: extraia o nome da assinatura/fechamento da mensagem
    (padrões como "Abraços, João") e use na saudação; se não houver, use uma
    saudação genérica como "Olá".

[6] Indicador de confiança: classifique a resposta como alta/média/baixa pela
    qualidade do match na base, e anexe um selo discreto (verde/amarelo/vermelho)
    no rascunho, só para revisão interna.

Edite ESTE workflow. Teste cada um com a entrada apropriada.

✅ Cómo verificar: [4] el borrador suena con el tono solicitado; [5] el saludo usa el nombre correcto (y recurre al genérico cuando no hay firma); [6] la etiqueta es coherente con qué tan bien respondió la base.

Conceptos clave

Uno a la vez

Capa por capa.

Nombra el workflow

Para editar, no para crear.

Error vs. calidad

Trata primero el error.

Probar el tipo correcto

Envía la entrada exacta.

6

🧩 Crear una skill / slash command

Qué es

El prompt para empaquetar una tarea repetida como skill: un archivo markdown (SKILL.md) con nombre, descripción, argumentos y pasos, que vive en .claude/skills y se convierte en un slash command invocable (p. ej.: /draft-email).

¿Qué es?Skill — un workflow en markdown, que se puede llamar bajo demanda. Comando slash — el atajo que activa la skill. Las skills se cargan solo cuando se invocan, así que no ocupan tanto contexto como un CLAUDE.md enorme.

Por qué aprender

Una skill acaba con tener que «volver a explicar»: ofrece consistencia (el mismo proceso cada vez), ahorro de contexto (se carga solo cuando la invocas) y reutilización (limpia la conversación y vuelve a invocarla con nuevos inputs). Si la invocas sin argumentos, la skill te pregunta qué falta.

🎯 Objetivo: crear una skill en el formato oficial (ejemplo: redactar un correo).

prompt (Plan Mode)
Crie uma skill no formato oficial do Claude Code, chamável como slash command.

Nome: <ex.: draft-email>
O que faz: <ex.: escrever um e-mail polido, conciso e sem enrolação>.
Argumentos esperados: <ex.: bullets com os pontos-chave, destinatário, tom>.
Comportamento: se eu invocar sem argumentos, pergunte o que faltar antes de
gerar. Salve a saída em <ex.: temporary/>.

Crie a estrutura .claude/skills/<nome>/SKILL.md com nome, descrição, argumentos
e passos. Depois me diga como invocá-la.

✅ Cómo verificar: existe .claude/skills/<nome>/SKILL.md. Limpia el contexto e invoca el slash command (p. ej., /draft-email) y confirma que solicite los datos de entrada y produzca la salida en el lugar correcto.

Conceptos clave

SKILL.md

Nombre, args, pasos.

.claude/skills

Dónde viven.

Comando slash

Cómo invocar.

Bajo demanda

Ahorra contexto.

⏰ Crear un agente programado

Qué es

El prompt para un agente que se ejecuta solo, según un horario (cron): cada mañana investiga un tema fijo, lo sintetiza y escribe una línea en una hoja de cálculo. Como nadie estará pendiente, el prompt debe contemplar el agentic gap desde el inicio: inputs fijos, salida estructurada, manejo de errores y registro en cada paso.

¿Qué es?Cron — un patrón de 5 campos (minuto, hora, día del mes, mes, día de la semana) que define cuándo ejecutar; 0 7 * * * = todos los días a las 7 h. Brecha agéntica — en producción, la IA no está observando para autocorregirse, así que los errores y los logs deben estar previstos.

Por qué aprender

Un agente que funciona sin ti solo es confiable si se diseñó para fallar con elegancia: registrar cada paso (para que puedas diagnosticar después), manejar los errores sin que todo se caiga y producir un resultado predecible. Pedirlo en el primer prompt es más barato que remendarlo después.

🎯 Objetivo: construir una tarea programada sin supervisión (investigación diaria → hoja de cálculo).

prompt (Plan Mode)
Entre em plan mode. Construa uma tarefa AGENDADA que roda sozinha, sem humano
presente, todo dia às <ex.: 8h> (cron).

O que ela faz a cada execução:
1. Pesquisa na web o tópico fixo "<ex.: novidades em automação com IA>"
   (definido no topo do arquivo, fácil de trocar).
2. Sintetiza os achados em um resumo curto.
3. Escreve uma linha na planilha <ex.: "Daily Research", aba Sheet1> com as
   colunas: data, tópico, resumo, fontes, status.

Requisitos para rodar sem supervisão (agentic gap):
- Inputs FIXOS (sem me fazer perguntas no meio da execução).
- Saída ESTRUTURADA e previsível.
- Trate erros sem derrubar a tarefa; se uma etapa falhar, registre e siga,
  gravando ao menos uma linha parcial com status de erro.
- Faça LOG claro em cada passo (mensagens específicas, não "falhou").
- Segredos vêm do ambiente, nunca do código nem do chat.

Antes de construir, planeje, me pergunte o que faltar e liste as credenciais.

✅ Cómo verificar: después del deploy, ejecútalo manualmente (no esperes al horario) y revisa el trace paso a paso. Confirma la fila en la hoja de cálculo y la programación (cron + próxima ejecución) en el panel. Fuerza un fallo y confirma que la tarea no se interrumpa y que registre el estado de error.

Conceptos clave

Cron

5 campos = cuándo.

Entradas fijas

Sin preguntas en medio.

Error + log

Desde el 1.er prompt.

Salida estructurada

Predecible.

🛡️ Frontend + auditoría de seguridad

Qué es

Dos prompts que cierran el ciclo de producción: uno para generar un frontend con personalidad (usando la skill de diseño, para que no parezca IA genérica) y otro para pedir una auditoría de seguridad rigorosa de la app antes de abrirla al mundo.

Por qué aprender

Una app abierta sin auditoría es un riesgo real: cualquiera con la URL puede activar tu workflow y consumir tus tokens (tú pagas por el uso de los demás). La auditoría verifica las rutas protegidas, que las claves no estén expuestas, que los secretos solo estén en variables de entorno y que los datos estén aislados por usuario (RLS).

🎯 Objetivo: generar un frontend con personalidad (no genérico).

prompt (frontend)
Crie o frontend para <ex.: o app de qualificação de leads>. USE a skill de
design de frontend para que NÃO fique com a cara genérica de site gerado por IA.

Estrutura desejada: <ex.: cabeçalho fixo com logo à esquerda e CTA à direita;
hero com texto grande e direto; um formulário que envia os dados e mostra o
resultado retornado pelo backend>.

A URL do backend e quaisquer chaves devem vir de variáveis de ambiente
(placeholder por enquanto). Me mostre o resultado para eu dar feedback
específico depois.

✅ Cómo verificar: el frontend tiene una identidad visual propia (no el diseño predeterminado de IA), el formulario funciona con un placeholder de backend y no aparece ninguna clave en el código del cliente.

🎯 Objetivo: auditar la seguridad de la app antes de abrirla.

prompt (auditoría — ejecútalo con el contexto limpio)
Aja como um especialista em segurança e faça uma auditoria detalhada deste app.
Verifique e me reporte achados + correções para cada item:

- Rotas protegidas: existe rota que dispara o backend sem autenticação?
- Chaves expostas: alguma chave/segredo aparece no código do frontend?
- Variáveis de ambiente: todos os segredos estão em env vars (e fora do git)?
- Isolamento de dados (RLS): um usuário consegue ver dados de outro mesmo com
  um bug no frontend?
- Abuso/custo: alguém com a URL consegue rodar o workflow e gastar meus tokens?

Liste os problemas por severidade e proponha a correção de cada um. Depois,
aplique as correções que eu aprovar.

✅ Cómo verificar: recibes una lista por nivel de gravedad. Ninguna clave en el frontend; las rutas que activan el backend requieren autenticación; los secretos solo en variables de entorno; RLS activa para aislar los datos por usuario. Corrige lo que falle y vuelve a auditar.

✓ App segura

  • ✓Las rutas que consumen tokens requieren iniciar sesión.
  • ✓Secretos solo en variables de entorno.
  • ✓RLS aísla los datos de cada usuario.

✗ App en riesgo

  • ✗App abierto: cualquiera gasta tus tokens.
  • ✗Clave de API en el código del frontend.
  • ✗Sin RLS: un error expone datos ajenos.

Conceptos clave

Skill de diseño

Frontend con identidad propia.

Rutas protegidas

Exigen inicio de sesión.

Secretos en env

Nunca en el frontend.

RLS

Aísla los datos.
