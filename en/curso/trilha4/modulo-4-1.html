MODULE 4.1

📦 Skills: Concept & Anatomy

A skill is an instruction file that becomes a reusable command: you describe a process once, and the agent starts executing it the same way every time — without you having to explain it again. Conceptually, it’s the W (workflows) of the WAT framework, except it lives in a folder and is triggered by a slash command. Here you’ll learn what a skill is, where it lives, what it’s made of, and when it makes sense to create one instead of just typing.

📦 What a skill is

What it is

A skill is, in essence, a instruction markdown file — conceptually identical to the layer W (workflows) of the framework WAT. The difference from a workflow you only describe in chat is where it lives e how it’s triggered: the skill is saved in a project folder and invoked with a command, so it can be run the same way as many times as you like, without you having to rewrite the process.

What is it?Workflow — a sequence of steps that solves a task (the “W” in WAT). Slash command — a command that starts with / and trigger an action in the agent (e.g., /clear). A skill is a packaged workflow exposed as a slash command.

The liberating detail: you don’t need to know how to write skills. You describe the workflow in natural language—"every time I ask, do X, then Y, then save to Z"—and ask the agent to turn this into a skill / slash command. It creates the file, and then you can call it with a command. It’s the same principle as vibe coding: describe the result, and AI does the heavy lifting.

Why learn

Skills solve four problems at once. Without them, you re-explain the same process every session, spend tokens repeating context, and lose consistency. Packaged as a skill, they provide:

  • •Consistency: the same process runs the same way every time, without re-explaining.
  • •Token efficiency: the skill loads on demand, only when invoked—it doesn’t take up context all the time.
  • •Shareable: is a file — you share it with the whole team.
  • •Reliable: wraps up complex steps that are easy to forget → you delegate and forget about it.

🎯 Goal: ask the agent to turn one of your workflows into a skill

prompt for the agent (copy and edit)
Transforme este workflow numa skill chamável (slash command).

Nome desejado: <nome-da-skill>
Quando deve ser usada: <descreva o gatilho — ex.: "quando eu pedir um resumo de reunião">
Argumentos que ela recebe: <ex.: texto-bruto, formato-de-saida>

1. <passo 1>
2. <passo 2>
3. <onde salvar / formato final>

Crie o arquivo em .claude/skills/ e me diga como invocá-la.

✅ How to verify: the agent should create the file and respond with the command /<nome-da-skill>. Run it once to confirm that it appears and prompts for the arguments.

📁 Where they live and how they become slash commands

What it is

Skills live in a project directory called .claude/skills. The organization is simple: each skill has its own folder, and inside it is a skill file that describes what it does. The agent scans that folder and exposes each skill as a slash command — a command that starts with / and what you type to trigger it.

What is it?Directory .claude — a configuration folder that the agent reads inside your project. Built-in — a command that’s ready to use (e.g., /clear clears the context). Your skills appear alongside the built-ins in the same slash command list.

Why learn

Understanding the place and the mechanism demystifies it: a skill isn’t a hidden AI feature, it’s a file in a folder that becomes a command. Note the recent unification: slash commands have been unified into skills — in other words, creating a skill and creating a slash command have become the same thing. That’s why comparing them with built-ins like /clear help: the only difference is that yours are defined by you, in the project.

Lifecycle of a skill

  1. 1

    Describe the workflow

    You describe the process in natural language — steps, inputs, output.

  2. 2

    Agent generates the skill file

    It creates the folder in .claude/skills with a name, description, and steps.

  3. 3

    Invoke with the slash command

    You type /nome-da-skill and the agent runs the process.

  4. 4

    Reuse (and share)

    The same run every time; and since it’s a file, it goes with the project for the team.

🧬 Anatomy of SKILL.md

What it is

Every skill has four essential parts: name (how it's called), description (o trigger — teaches the agent WHEN use the skill), expected arguments (the inputs it receives) and the step-by-step instructions (what to do). The most underrated piece is the description: it isn’t decorative—it’s what lets the agent decide on its own that this is the right skill for the situation.

What is it?Trigger — the condition that causes the skill to be selected. A good description says “use this WHEN...”. If it’s vague, the agent won’t know when to apply it; if it’s precise, it gets it right on its own.

🎯 Goal: create the file that defines a callable skill

.claude/skills/draft-email/SKILL.md (copy and edit)
---
name: <nome-da-skill>
description: <quando-acionar — ex.: rascunhar um e-mail a partir de bullets>
---

# <Título da skill>

## Argumentos
- destinatario: <quem recebe>
- tom: <profissional | casual>
- bullets: <pontos-chave do e-mail>

## Passos
1. Leia os <bullets> e o <tom>.
2. Escreva um e-mail polido, conciso, sem enrolação.
3. Salve em temporary/<nome-arquivo>.md

✅ How to verify: run /<nome-da-skill> — if the skill appears in the slash commands list and asks for any missing arguments, it's registered.

Why learn

Understanding the anatomy gives you control even without writing code: you know how to request a good trigger description (“use when I paste email bullets”), name clear arguments, and list steps in the right order. And you know how to review what the agent generated—if the description is weak, just ask it to make it more specific. The structure frontmatter (name + description) + body (arguments + steps) is the skeleton of every skill.

🔧 Skills can call tools

What it is

A skill doesn’t replace the tools (tools) — it orchestrates. Within your steps, a skill can still trigger tools: Python scripts that search the web, scrape a page, or generate a document. In other words, the WAT remains intact underneath: the skill is the W (workflow), the tool is the T (tool), and the agent decides when to run each tool during the process.

What is it?Tool (utility) — a piece of code that performs a concrete action in the world (search, scraping, saving a file). WAT — the Workflows + Agents + Tools framework: skills are the workflows, tools are the tools, and the agent ties everything together.

Why learn

Knowing that skill ≈ W and tool ≈ T avoids a common confusion: thinking that adopting skills throws away everything you’ve learned about tools and MCP. It doesn’t. A skill simply gives you a outline reusable guide to when and how to use your tools. A "market research" skill, for example, might say: search the web, scrape the first three pages, summarize them, and generate a document — calling a tool at each step.

⚖️ When to use a skill vs. type

What it is

Not everything deserves to become a skill. The rule: create a skill when the process repeats, consistency matters, the instructions are complex or easy to forget, or you want to share it with the team. For everything else—a one-sentence task, an initial experiment, a simple instruction—it’s faster to just type. Packaging a trivial task into a skill only adds ceremony.

What is it?Ceremony — the extra effort of formalizing something (creating a file, naming it, documenting it). It’s worth it when you’ll reuse it; it’s wasteful for a one-off request.

Why learn

The criteria avoid both extremes: never using skills (and re-explaining everything every time) or turning anything into a skill (and cluttering the folder with commands you use only once). The key question is simple: "will I repeat this?" If so, and consistency matters, a skill is worthwhile. If it’s a one-off, type it.

✓ Create a SKILL when…

  • ✓The workflow repeats (you’ve already done this 3+ times).
  • ✓Consistency matters (same format/quality every time).
  • ✓The instructions are complex or easy to forget.
  • ✓You want to share the process with the team.

✗ Only TYPE when…

  • ✗It’s a one-off task described in a single sentence.
  • ✗You’re still experimenting / exploring the problem.
  • ✗The instruction is simple and is not repeated.
  • ✗Making it formal would cost more than simply asking again.

🪶 Skills vs CLAUDE.md (on-demand context)

What it is

The division of labor: the CLAUDE.md stores only what applies to every session — the project's purpose, goal, framework, general rules. It is always in context. What is task-based (per-task) goes to skills, which carry on demand — only when you invoke that command. It’s the difference between “what the AI always needs to know” and “what it only needs when doing X.”

What is it?CLAUDE.md — memory file that the agent reads at the start of every session. On-demand context — load information only when it's needed, so it doesn't take up "working memory" all the time.

Illustrative diagram — putting everything in CLAUDE.md fills up the fixed context; keeping per-task instructions in skills makes dozens of commands available without adding weight, because only the one you invoke is loaded.

Why learn

The classic beginner mistake is put everything in CLAUDE.md — every instruction, every workflow, every detail. This exceeds the context: the file gets huge, takes up space in every session, and degrades the AI’s attention. That’s exactly the point of skills: you can have 20, 50 skills without making anything bloated, because they only load when called. A concise CLAUDE.md + many on-demand skills > a giant CLAUDE.md.

✓ In CLAUDE.md (every session)

  • ✓Project purpose and objective.
  • ✓The framework / general conventions.
  • ✓Rules that apply in any task.

✗ NOT in CLAUDE.md → goes in a skill

  • ✗Workflows for a single specific task.
  • ✗Long, detailed step-by-step instructions for a process.
  • ✗Everything that matters only when you're going to do X.

🎯 Practical tip

Before adding anything to CLAUDE.md, ask: "does this apply to every session, or only when I do a specific task?" If it’s specific, turn it into a skill. Your CLAUDE.md should fit at a glance; the rest of the knowledge lives in the skills folder, ready to be called.

🤝 Share and version

What it is

Since a skill is just a file in a folder of the project, it inherits all the advantages of a code file: it can be versioned in Git (change history, review, rollback), and shared with anyone who clones the project. The process stops being knowledge trapped in one person’s head and becomes a team asset.

What is it?Git — the system that tracks file version history. Version control — track every change to a file over time so you can view, review, and revert it. Since a skill is a file, it fits right into this workflow.

Why learn

This is the leap from "personal trick" to "team capability." When your best workflow becomes a versioned skill, any colleague can run the same process, with the same quality, without having to ask you how. Fixes to the skill benefit everyone the next time it's invoked. This is real reuse: write it once, and the whole team benefits.
