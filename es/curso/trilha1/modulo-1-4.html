1

🧬 Agéntico

Qué es

Un agente es un sistema que recibe un objetivo y razona, se adapta y se autocorrige para alcanzarlo, en vez de seguir pasos fijos. Agéntico es el adjetivo: describe ese comportamiento de «decidir el camino». Para construir agentes de forma organizada existe el WAT (Workflows / Agent / Tools): W son las instrucciones en markdown (el «manual»), A es el agente coordinador (el «cerebro»), T son las herramientas/scripts que hacen el trabajo.

Lo que hace poderoso al agente es el ciclo de autom mejora: se ejecuta, encuentra un error, lo diagnostica, corrige la herramienta y actualiza el manual — para que el error no vuelva. Pero hay una trampa: el agentic gap ("brecha agéntica"): cuando el agente se ejecuta solo en la nube, nadie lo supervisa para que se autocorrija, así que la confiabilidad pasa a ser tu responsabilidad.

Diagrama ilustrativo — W alimenta A (cian), que activa T; la línea discontinua es el ciclo de automejora que cierra el bucle.

GlosarioVocabulario agéntico

Agente
Sistema que razona, se adapta y se corrige solo para alcanzar un objetivo. Ej.: investiga un tema y entrega un informe por su cuenta.
Agéntico
El comportamiento de decidir el camino, en lugar de seguir un guion fijo. Ej.: elige qué herramientas usar.
WAT (Workflows / Agent / Tools)
Estructura: instrucciones + coordinador + scripts. Ej.: W indica qué hacer, A decide, T ejecuta.
Loop de mejora continua
Fallar → diagnosticar → corregir la tool → actualizar el workflow. Ej.: el error no vuelve en la siguiente ejecución.
Brecha agéntica
En la nube, nadie está mirando para autocorregir. Ej.: un fallo puede pasar desapercibido — exige logs y alertas.

Por qué aprender

Estas palabras explican la diferencia entre «se ejecutó frente a mí» y «se ejecuta solo con seguridad». El ciclo de autom mejora es lo que hace que el agente mejore con el uso; el agentic gap es la razón por la que tienes que pensar en la confiabilidad desde el primer prompt cuando vas a alojar.

Conceptos clave

Agente

Razona y se adapta.

WAT

Workflows, Agent, Tools.

Automejora

El error no vuelve.

Brecha agéntica

Sin autocuración en la nube.

2

🔎 RAG

Qué es

RAG (Retrieval-Augmented Generation, "generación aumentada por recuperación") es la técnica de hacer que la IA buscar la información correcta en tus documentos antes de responder, en vez de adivinar de memoria. Los documentos forman la knowledge base ("base de conocimiento"). El acto de buscar y traer el fragmento relevante es la recuperación de información ("recuperación").

Para que el agente sepa cuánto puede confiar en lo que encontró, puede emitir un confidence score ("nivel de confianza"): alto, medio o bajo, según qué tan bien coincida la base con la pregunta. Si la confianza es baja (o no encontró nada), el agente se niega a inventar y recurre a un plan B cortés («voy a investigar y te respondo»), lo opuesto a alucinar.

GlosarioRAG y recuperación

RAG
La IA busca en tus documentos antes de responder. Ej.: cita la política de cambios en vez de inventar un plazo.
Knowledge base
El conjunto de documentos que consulta la IA. Ej.: el PDF de políticas + las preguntas frecuentes de la tienda.
Retrieval (recuperación)
Buscar y traer el fragmento relevante. Ej.: encontrar la sección de garantía para responder sobre una TV.
Confidence score
Qué tan bien coincidió la base (alta/media/baja). Ej.: baja → no responde, lo deriva a investigación.

Por qué aprender

RAG es lo que transforma un chatbot genérico en un agente que responde sobre el tu negocio con hechos verificables. Y el confidence score es la pieza de seguridad: hace que el agente diga "no sé" en lugar de mentir con confianza, exactamente el comportamiento que verificas con "confía, pero verifica".

✓ RAG bien hecho

  • ✓Responde citando tus documentos.
  • ✓Emite un confidence score y usa fallback cuando es bajo.
  • ✓Se niega a inventar lo que no está en la base.

✗ Señales de un RAG deficiente

  • ✗Inventar plazos/números que no están en los documentos.
  • ✗Responder con confianza incluso sin encontrar nada.
  • ✗Ignorar la nota de confianza (sin plan B).

Conceptos clave

RAG

Buscar antes de responder.

Knowledge base

Tus documentos.

Retrieval

Traer el fragmento correcto.

Confianza

¿No sabes? No inventes.

🐙 Control de versiones en la nube

Qué es

GitHub es un repositorio de código en la nube: el lugar donde vive el código, accesible desde cualquier máquina, con un historial completo para volver atrás. Cada proyecto queda en un repo (repositorio) — la carpeta del proyecto dentro de GitHub. Guardas los cambios en commits (instantáneas del proyecto con una descripción) y envía esos commits a la nube con un push.

Para que el asistente opere GitHub desde la terminal, se usa la gh CLI ("interfaz de línea de comandos de GitHub"): la herramienta que conecta tu máquina con tu cuenta. Y recuerda la regla de oro: el .env (con las claves) nunca entra en un commit: el .gitignore garantiza eso.

GlosarioGit y nube

GitHub
Almacenamiento de código en la nube, con historial. Ej.: el deploy obtiene el código de ahí, no de tu máquina.
Repo (repositorio)
La carpeta del proyecto dentro de GitHub. Ej.: un repo privado llamado "automacoes".
Commit
Una foto guardada del proyecto con una descripción. Ej.: «agrega manejo de errores en el nodo X».
Push
Enviar los commits locales a GitHub. Ej.: «push» después de iterar en el código.
gh CLI
La herramienta de línea de comandos de GitHub. Ej.: el asistente la usa para conectarse y enviar.

Por qué aprender

GitHub es la base de todo lo que se ejecuta alojado: el código debe estar en la nube para que un servicio de ejecución lo descargue y lo ejecute. El historial de commits también es tu respaldo: si algo se rompe, vuelves a una versión que funcionaba. Y entender commit/push/repo te permite seguir lo que hace el asistente, en vez de solo aprobar a ciegas.

Conceptos clave

GitHub

Código en la nube.

Repo

La carpeta del proyecto.

Commit / push

Guarda y envía.

.env fuera

El secreto nunca se sube.

4

☁️ Ejecución alojada

Qué es

Trigger.dev es un motor de ejecución en la nube: ejecuta tus tareas de forma confiable, sin timeout, con reintentos y logs, como un asistente que hace el trabajo en el momento adecuado. Activa tareas por cron (un reloj de programación, un patrón de 5 campos como 0 7 * * * = "todos los días a las 7 h") o por webhook (una «campana digital»: una URL que, al recibir datos, activa la tarea).

Los datos que llegan por el webhook son el payload ("carga"). Construyes y pruebas en un entorno de dev (desarrollo) antes de promover a prod (producción), el entorno en vivo. Cada ejecución deja un trace (registro paso a paso); los fallos pueden activar reintentos (reintentos) y alerts (notificaciones por correo electrónico/Slack).

GlosarioEjecución en la nube

Trigger.dev
Motor de ejecución en la nube (sin timeout, con reintentos y registros). Ej.: ejecuta la tarea todos los días a las 8h.
Cron
Programación por reloj, 5 campos. Ej.: 0 7 * * * = todos los días a las 7 h.
Webhook
URL que activa la tarea al recibir datos. Ej.: un formulario envía datos y activa el informe.
Payload
Los datos que llegan por el webhook. Ej.: nombre de la empresa, sector, objetivo en un JSON.
Dev vs. prod
Entorno de pruebas vs. entorno en vivo. Ej.: probar en dev, promover a prod.
Trace · retry · alert
Rastro de la ejecución, nuevos intentos, avisos de falla. Ej.: 3 reintentos con espera; alerta por correo electrónico.

Por qué aprender

Este es el vocabulario que cierra el agentic gap. Sin nadie supervisando, son los traces que te muestran lo que pasó, los reintentos que resuelven fallas pasajeras y los alerts que te avisan antes que al usuario. Cuidado: retry corrige errores temporales (de red/tiempo), no errores de lógica — saber la diferencia evita "volver a intentarlo" para siempre.

🎯 Consejo práctico

Construye y prueba siempre en dev; solo promueve a prod cuando esté listo. Y configura alertas de error en cada tarea alojada, así descubres que algo se rompió antes de que un usuario te avise.

Conceptos clave

Trigger.dev

Motor de ejecución.

Cron / webhook

Por agenda o evento.

Dev → prod

Prueba y luego en vivo.

Trace/retry/alert

Visibilidad en la nube.

🖥️ App / Frontend

Qué es

O frontend es todo lo que el usuario ve y toca: botones, formularios, textos, diseño; se ejecuta en el navegador de la persona. El backend es lo que se ejecuta en el servidor: la lógica, las llamadas a la API, la base de datos, invisible para el usuario. Los dos se comunican en un ciclo de request/response ("solicitud/respuesta"): el usuario hace clic → se envía una solicitud al servidor → se procesa → vuelve la respuesta → se actualiza la pantalla.

Para publicar un frontend en internet se usa la Vercel: un servicio de alojamiento de sitios web — haces push en GitHub y publica el sitio, accesible desde cualquier lugar. Y los secretos de la app (como la clave que conecta el frontend con el backend) quedan en variables de entorno (variables de entorno): valores que se inyectan en tiempo de ejecución, fuera del código.

Diagrama ilustrativo — el frontend (emerald) solicita, el backend (cian) procesa y responde. Ese ida y vuelta es el ciclo request/response.

GlosarioApp y web

Frontend
Lo que ves y tocas en el navegador. Ej.: el formulario y el resultado en pantalla.
Backend
La lógica en el servidor (API, base de datos). Ej.: la IA que analiza y calcula la puntuación del lead.
Solicitud / respuesta
Se envía el pedido, vuelve la respuesta y se actualiza la pantalla. Ej.: hace clic en «generar» → recibe el análisis.
Vercel
Alojamiento de sitios web; un push en GitHub publica. Ej.: el frontend queda accesible mediante una URL.
Env var (variable de entorno)
Secreto inyectado en tiempo de ejecución, fuera del código. Ej.: la clave que conecta el frontend con el backend.

Por qué aprender

La separación entre frontend/backend es el modelo mental que te permite entender cualquier app. También es lo que conecta tu workflow con el mundo: al cambiar el disparador del formulario por un webhook, cualquier persona con la URL puede usar tu automatización a través de un sitio atractivo: el frontend en Vercel se comunica con el backend.

Conceptos clave

Frontend

Lo que se ve.

Backend

La lógica en el servidor.

Vercel

Publica el sitio.

Env var

Secreto en tiempo de ejecución.

🔐 Seguridad y pago

Qué es

Cuando la app tiene usuarios, necesitas proteger los datos y cobrar. El Supabase es un servicio de base de datos + inicio de sesión (autenticación). Dentro de él, el RLS (Row-Level Security, "seguridad a nivel de fila") son reglas que residen en la propia base de datos para que un usuario nunca vea los datos de otro: una capa extra, incluso si hay un bug en el frontend. Los cambios en la estructura de la base de datos son migrations (scripts que crean o modifican tablas).

Para recibir pagos existe el Stripe. El usuario paga en una página de checkout ("finalizar compra"); cada plan tiene un price ID (el identificador del precio). Stripe avisa a tu aplicación sobre los eventos (suscripción, cancelación) mediante un webhook, validado por un secreto del webhook (la contraseña que confirma que el aviso realmente provino de Stripe). Un modelo común es el freemium: un nivel gratuito limitado + uno pago ilimitado.

GlosarioSeguridad y pagos

Supabase
Base de datos + inicio de sesión (autenticación). Ej.: guarda a los usuarios y los datos de cada uno.
RLS (Row-Level Security)
Reglas en la base de datos que aíslan los datos por usuario. Ej.: nadie ve los leads de otra persona.
Migration
Script que crea o modifica tablas en la base de datos. Ej.: crear la tabla «suscripciones».
Stripe
Servicio de pagos. Ej.: cobra la suscripción mensual del plan pro.
Checkout / price ID
Página de pago / identificador del precio. Ej.: el checkout del plan "$29/mês".
Webhook secret / freemium
Contraseña que valida el aviso de Stripe / modelo gratis+pago. Ej.: confirma «se suscribió» y habilita el uso ilimitado.

Por qué aprender

Estos términos cierran el ciclo «idea → app que genera dinero de forma segura». Sin autenticación y RLS, cualquiera con la URL usa tu app (y genera gastos); sin RLS, un bug puede filtrar los datos de un usuario a otro. Y el modelo freemium con Stripe es lo que convierte un workflow en un producto que se paga solo.

✓ App protegida

  • ✓Autenticación (Supabase) + RLS para aislar los datos.
  • ✓Secretos solo en variables de entorno; el webhook secret valida.
  • ✓Auditoría de seguridad antes de publicar.

✗ App en riesgo

  • ✗App abierto: alguien gasta tus tokens de IA.
  • ✗RLS desactivado: los datos de un usuario se filtran a otro.
  • ✗Clave expuesta en el frontend o incluida en un commit.

Tu app tiene inicio de sesión, pero quieres asegurarte de que un usuario nunca vea los datos de otro, incluso con un bug en el frontend. ¿Qué pieza resuelve esto?

Conceptos clave

Supabase

Base de datos + inicio de sesión.

RLS

Aísla los datos en la base de datos.

Stripe

Recibe pagos.

Freemium

Gratis + de pago.
