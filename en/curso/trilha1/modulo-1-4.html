🧬 Agentic

What it is

A agent is a system that receives a goal and reasons, adapts, and self-corrects to reach it—instead of following fixed steps. Agentic is the adjective: it describes this “choosing the path” behavior. To build agents in an organized way, there’s the WAT (Workflows / Agent / Tools): W are the markdown instructions (the "manual"), A is the coordinating agent (the “brain”), T are the tools/scripts that do the work.

What makes the agent powerful is the self-improvement loop: it runs, hits an error, diagnoses it, fixes the tool, and updates the manual so the error doesn’t happen again. But there’s a catch: the agentic gap ("agentic gap") — when the agent runs on its own in the cloud, no one is watching to heal it, so reliability becomes your responsibility.

Illustrative diagram — W feeds A (cyan), which triggers T; the dashed line is the self-improvement loop that closes the cycle.

GlossaryAgentic vocabulary

Agent
A system that reasons, adapts, and self-heals toward a goal. E.g., researches a topic and delivers a report on its own.
Agentic
The behavior of choosing a path instead of following a fixed script. E.g.: it chooses which tools to use.
WAT (Workflows / Agent / Tools)
Structure: instructions + coordinator + scripts. E.g.: W says what to do, A decides, T executes.
Self-improvement loop
Make a mistake → diagnose → fix the tool → update the workflow. E.g., the error doesn’t come back on the next run.
Agentic gap
In the cloud, no one is watching it self-heal. E.g., a failure can go unnoticed — requires logs and alerts.

Why learn

These words explain the difference between "it ran in front of me" and "it runs safely on its own." The self-improvement loop is what makes the agent better with use; the agentic gap is why you have to think about reliability from the very first prompt when you're going to host it.

Key concepts

Agent

Reasons and adapts.

WAT

Workflows, Agent, Tools.

Self-improvement

The error doesn’t come back.

Agentic gap

No self-healing in the cloud.

🔎 RAG

What it is

RAG (Retrieval-Augmented Generation, "retrieval-augmented generation") is the technique of making AI search the right information in your documents before answering — instead of guessing from memory. The documents form the knowledge base ("knowledge base"). The act of searching for and retrieving the relevant passage is called retrieval ("retrieval").

So the agent knows how much it can trust what it found, it can emit a confidence score ("confidence score"): high, medium, or low, depending on how well the knowledge base matches the question. If confidence is low (or nothing is found), the agent refuses to make things up and falls back to a polite plan B ("I'll look it up and get back to you")—the opposite of hallucinating.

GlossaryRAG & retrieval

RAG
AI searches your docs before answering. E.g.: cite the return policy instead of making up a timeframe.
Knowledge base
The set of documents the AI consults. E.g.: the policy PDF + the store FAQ.
Retrieval (information retrieval)
Search and retrieve the relevant passage. E.g.: find the warranty section to answer a question about a TV.
Confidence score
How well the knowledge base matched (high/medium/low). E.g.: download → no response, forward for research.

Why learn

RAG is what turns a generic chatbot into an agent that answers questions about the your business with verifiable facts. And the confidence score is the safety feature: it makes the agent say “I don’t know” instead of confidently making things up — exactly the behavior you verify with “trust but verify.”

✓ Well-done RAG

  • ✓Answers by citing your documents.
  • ✓It emits a confidence score and uses a fallback when it’s low.
  • ✓Refuses to make up what isn’t in the knowledge base.

✗ Signs of poor RAG

  • ✗Make up deadlines/numbers that aren’t in the docs.
  • ✗Answer confidently even without finding anything.
  • ✗Ignore the confidence note (no fallback plan).

Key concepts

RAG

Search before responding.

Knowledge base

Your documents.

Retrieval

Bring in the right excerpt.

Confidence

Don't know? Don't make it up.

🐙 Cloud versioning

What it is

GitHub is a cloud code repository: the place where code lives, accessible from any machine, with a complete history you can use to roll back. Each project lives in a repo (repository) — the project folder in GitHub. You save changes in commits (snapshots of the project with a description) and sends those commits to the cloud with a push.

To let the assistant operate GitHub through the terminal, use the gh CLI ("GitHub command-line interface"): the tool that connects your machine to your account. And remember the golden rule: the .env (with the keys) never goes into a commit — the .gitignore ensures that.

GlossaryGit & cloud

GitHub
Cloud code storage with history. E.g., the deploy pulls the code from there, not from your machine.
Repo (repository)
The project folder inside GitHub. E.g., a private repo called "automacoes".
Commit
A saved snapshot of the project with a description. E.g.: "add error handling to node X".
Push
Push local commits to GitHub. E.g.: "push" after iterating on the code.
gh CLI
GitHub's command-line tool. E.g.: it uses it to connect and send.

Why learn

GitHub is the foundation for everything that runs hosted: the code needs to be in the cloud so a runtime service can pull it and run it. The commit history is also your safety net — if something breaks, you can go back to a version that worked. And understanding commit/push/repo lets you follow what the assistant is doing instead of just approving blindly.

Key concepts

GitHub

Cloud code.

Repo

The project folder.

Commit / push

Save and send.

.env outside

Secrets never get pushed.

☁️ Hosted execution

What it is

Trigger.dev is a cloud execution engine: it runs your tasks reliably, without timeouts, with retries and logs — like an assistant that gets the work done at the right time. It triggers tasks through cron (a scheduling clock — a 5-field pattern like 0 7 * * * = "7 a.m. every day") or with webhook (a “digital doorbell”: a URL that wakes up the task when it receives data).

The data that arrives through the webhook is the payload ("load"). You build and test in a dev (development) before promoting to prod (production), the live view. Each run leaves a trace (step-by-step trail); failures can trigger retries (retries) and alerts (email/Slack notifications).

GlossaryCloud execution

Trigger.dev
Cloud execution engine (no timeout, with retries and logs). E.g., run the task at 8 a.m. every day.
Cron
Clock-based scheduling, 5 fields. E.g.: 0 7 * * * = 7 a.m. daily.
Webhook
URL that wakes up the task when it receives data. E.g., a form submits data and triggers the report.
Payload
The data that arrives through the webhook. E.g.: company name, industry, objective in a JSON.
Dev vs. prod
Test environment vs. live environment. E.g., test in dev, promote to prod.
Trace · retry · alert
Execution trail, retries, failure warnings. E.g.: 3 retries with a wait; email alert.

Why learn

This is the vocabulary that closes the agentic gap. Without anyone watching, these are the traces that show you what happened, the retries that resolve temporary failures and the alerts that alert you before the user does. Be careful: retries fix temporary errors (network/timeouts), not logic bugs — knowing the difference keeps you from retrying forever.

🎯 Practical tip

Always build and test in dev; only promote to prod when it's ready. And configure failure alerts on every hosted task — that way, you find out something broke before a user does.

Key concepts

Trigger.dev

Execution engine.

Cron / webhook

By schedule or event.

Dev → prod

Test, then go live.

Trace/retry/alert

Visibility in the cloud.

🖥️ App / Frontend

What it is

O frontend is everything the user sees and interacts with: buttons, forms, text, layout — it runs in the person’s browser. The backend is what runs on the server: the logic, API calls, database — invisible to the user. The two communicate in a request/response ("request/response"): the user clicks → a request goes to the server → it processes it → the response comes back → the screen updates.

To publish a frontend on the internet, use the Vercel: a website hosting service—you push to GitHub and it puts the site online, accessible from anywhere. And the app’s secrets (such as the key that connects the frontend to the backend) stay in env vars (environment variables): values injected at runtime, outside the code.

Illustrative diagram — the frontend (emerald) makes a request, the backend (cyan) processes it and responds. This back-and-forth is the request/response cycle.

GlossaryApp & web

Frontend
What the user sees and interacts with in the browser. E.g., the form and the result on the screen.
Backend
The server-side logic (API, database). E.g.: the AI that analyzes and calculates the lead score.
Request / response
Request goes out, response comes back, screen updates. E.g.: click "generate" → receive the analysis.
Vercel
Website hosting; a push to GitHub publishes it. E.g., the frontend is accessible through a URL.
Env var (environment variable)
Secret injected at runtime, outside the code. E.g.: the key that connects the frontend to the backend.

Why learn

The frontend/backend separation is the mental model that unlocks understanding any app. It's also what connects your workflow to the world: replace the form trigger with a webhook, and anyone with the URL can use your automation through a polished website—the frontend on Vercel talking to the backend.

Key concepts

Frontend

What you see.

Backend

The server-side logic.

Vercel

Publish the site.

Env var

Secret at runtime.

🔐 Security & payments

What it is

When the app has users, you need to protect data and charge. The Supabase is a database + login (authentication) service. Inside it, the RLS (Row-Level Security, "row-level security") are rules that live in the database itself so one user never sees another user’s data—an extra layer, even if there’s a bug in the frontend. Changes to the database structure are migrations (scripts that create/modify tables).

To receive payments, there’s Stripe. The user pays on a checkout ("checkout"); each plan has a price ID (the price ID). Stripe notifies your app about events (subscribed, canceled) via webhook, validated with a webhook secret (the password that confirms the notification really came from Stripe). A common model is the freemium: a limited free tier + an unlimited paid tier.

GlossarySecurity & payments

Supabase
Database + login (authentication). E.g.: stores users and each user's data.
RLS (Row-Level Security)
Database rules that isolate data by user. E.g.: no one can see another person's leads.
Migration
Script that creates/changes tables in the database. E.g.: create the "subscriptions" table.
Stripe
Payment service. E.g.: charge the monthly subscription fee for the pro plan.
Checkout / price ID
Payment page / price ID. E.g., the checkout for the "$29/month" plan.
Webhook secret / freemium
Password that validates the Stripe notice / free+paid model. E.g.: confirm "subscribed" and unlock unlimited access.

Why learn

These terms complete the cycle from "idea → app that safely makes money." Without authentication and RLS, anyone with the URL can use your app (and spend money); without RLS, a bug can leak one user's data to another. And freemium with Stripe is what turns a workflow into a product that pays for itself.

✓ Protected app

  • ✓Authentication (Supabase) + RLS isolating data.
  • ✓Secrets only in env vars; webhook secret validation.
  • ✓Security audit before going live.

✗ App at risk

  • ✗Open app: someone spends your AI tokens.
  • ✗RLS off: one user’s data leaks to another.
  • ✗Key exposed in the frontend or committed.

Your app has login, but you want to make sure that one user never sees another user's data, even with a frontend bug. Which component fixes this?

Key concepts

Supabase

Database + login.

RLS

Isolates data in the database.

Stripe

Accepts payments.

Freemium

Free + paid.
